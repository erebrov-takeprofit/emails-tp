TakeProfit — Email Templates

Hand-coded, email-client-safe HTML for TakeProfit's transactional & notification emails. This page is a live index of the built templates, the design system guide, and the master content table.

📋 Notion — email table 📐 Design system guide 💻 GitHub repo

About this project

Each file below is one email template — pure table-based HTML with inline styles, built to render across Apple Mail, iOS, Gmail and Outlook (no flexbox/grid/JS). Images are served from AWS S3 (takeprofit-static.s3.eu-central-1.amazonaws.com), so this repo holds only HTML. Backend fills the {...} placeholders when sending.

The design system guide is the portable spec: tokens, components, footer variants, per-email subjects & preheaders. It's what keeps every email visually consistent.

How it works & how to update

Editing flow

  1. Draft & prompt in the Claude project “Email | Design, texts and coding rules” — the place for wording, subjects and coding rules.
  2. Edit the HTML in the git repo (one file per email). Filenames are kebab-case and mirror the email name.
  3. Log the change — add a dated entry to the Changelog below, with a rollout badge saying whether it is live on prod, rolling out, or repo-only.
  4. Push to main → Netlify auto-deploys → the preview URLs update. This updates the previews only — the emails users receive change when the backend picks the template up, so a merged change stays Rolling out until someone confirms it arrives from prod.
  5. Update the Notion table — subject, preheader, status, owner, variant, preview URL. Notion is the source of truth for metadata.

Single source of truth

  1. HTML + guide.md → this git repo (canonical).
  2. Email metadata (subjects, triggers, owners, statuses) → Notion table.
  3. Prompting / texts → Claude project. Point it at the repo rather than pasting a static copy, so it always reads the latest guide.

Letter 1 — tried to connect (1 059 addresses: opened the connect panel, picked an exchange or started a connection) and Letter 2 — no attempt yet (1 383: has an account, never took a step towards connecting).   • utm_content renamed with the segments: letter1_tried and letter2_no_attempt. utm_campaign=bybit_rebates_2026_09 is unchanged.
  • Deliverability, not geo, is the reason to stage the send: 60 addresses sit on rare domains and 172 have no product event in 400 days. Send those first and watch the bounce rate before the rest goes out.

September 8, 2026August digest: 75/25 split via four variations — Customer.io cannot weight an A/B testCustomer.io▸
  • Customer.io splits an A/B test evenly, full stop. Verified against the schema the UI itself uses: POST /newsletters/{id}/tests takes no request body, the template object has no weight field (only test_group_id, an index), and update_type: "test" exposes just platform, tracked, automatic_winner, test_metric, test_duration. The “A — 50%” badges are derived (100 / variations), not settings.
  • The workaround: more variations. send_percentage is the share of the audience entering the test, not the ratio between arms — changing it costs a second wave via end_test. Duplicating the control instead gets an uneven split in one wave: four variations at 25% each, three carrying the same subject, is 75/25. Five would be 80/20; the cap is eight.
  • Applied to send 74: two extra variations, now templates 106 (group 0), 107 (group 1), 109 (group 2), 110 (group 3). POST .../tests clones the control whole — subject, preheader and body — so the two new ones arrived as exact copies of A with no edit needed. Verified server-side: all four bodies byte-identical, exactly 2 distinct subjects and 2 distinct preheaders, so arm A is 3×25% and arm B is 25%.
  • Read the result on human_opened, not opened. July delivered 37 004 and logged 7 397 opens — but 3 872 of those were prefetch (Apple MPP and friends) against 4 213 human. Roughly half the open events never saw a subject line, so judging on the headline number halves the measured difference. Clicks (317, human 304 — 0.8%) are too thin to pick a winner on.
  • What the perk costs: template_metrics reports per template, so the three A rows must be summed by hand, and the built-in “Chance to Beat Original” becomes noise — it compares identical copies against each other. Four bodies to keep in sync instead of two. Sensitivity barely moves: minimum detectable difference on human opens goes from 0.93 p.p. at 50/50 to 1.07 p.p. at 75/25 (1.16 at 80/20), because the base is large.
  • Send still a draft: sent_at / scheduled_at null, sending false, send_percentage 100, no automatic winner. Audience, goal, updates tag, rate limits and From / Reply-To untouched.
  • Open — variant A’s preheader still reads “Build synthetic search formulas, stream live feeds”, naming the same two features its new subject already names. It now lives in three templates, so changing it is three edits.
